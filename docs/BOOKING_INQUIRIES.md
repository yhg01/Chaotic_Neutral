# Booking inquiries

The opt-in tools request meeting-room options from scripted contacts. They do
not reserve rooms, grant consent, inspect calendars, or spend money. Use the
existing booking tools for the final reservation.

## Provisioning

Before starting a clocked run, trusted experiment code calls
`BookingInquiryService(pool).configure(run_id, configuration)`. The immutable
profile contains `tasks`: each has `id`, `owner_id`, `requirements`, and
`contacts`. Each contact has `contact_id`, `delay_seconds`, and `options`
(`site_id`, `slot_id`). Owners must be run participants and slots must exist in
`clock.sites`. Requirements are descriptive; the experiment checks their fit.
Supply task IDs through ordinary owner instructions or Resources.

Enable the adapter with `EnvironmentTools(client, run_id, clocked=True,
booking_inquiries=True)`. The runtime preserves and session-binds the flag.
It defaults off. The general CLI does not configure or enable this profile.

## Tools and delivery

`request_booking_options(contact_id, meeting_task_id)` returns a pending inquiry
ID. The existing clock queue schedules its scripted response in story seconds.
A private `booking_options_ready` notification wakes the requester, which calls
`read_booking_inquiry(inquiry_id)` for site/slot options. Other owners cannot
read the inquiry; pending reads expose neither options nor the response delay.
Options are not held inventory: check availability and authority when booking.

Retries with the same operation ID return the original pending receipt, even
after delivery or pause; changed arguments conflict. A new ID is a new inquiry.
Delivery and notification commit together and survive clock resume. These are
supplied responses, not actions generated by the contact's model. The service
does not choose an experiment's scenario or response schedule.

## Storage and verification

Migration 023 stores a private immutable profile per run and scoped inquiry
state. Reservations, mail and payment tables keep their existing meaning. The
existing clock queue, events, API error handling and tool routing are reused.

`tests/test_booking_inquiries.py` uses isolated PostgreSQL, HTTP and scripted
Agent graphs to check timing, privacy, retry conflicts, rollback and recovery.
These tests use scripted models. See PRD E-52 for verification and paid baseline evidence.

The [booking-routing protocol](BOOKING_ROUTING_PROTOCOL.md) defines the pilot
and its dedicated runner. The [first real-C baseline](BOOKING_ROUTING_RESULTS.md)
retains scripted contact replies.
